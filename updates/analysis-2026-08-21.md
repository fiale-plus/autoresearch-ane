## Part 2 — Mechanics that actually govern the score (source-verified)

Four findings from reading `train_ane.m` change the interpretation of the whole history:

### 2.1 Resume clobbers `LEARNING_RATE` and `TOTAL_STEPS` — LR sweeps were no-ops

`load_checkpoint()` (`ane/train_ane.m:192`) unconditionally overwrites `lr` and `total_steps` from the checkpoint header, and `save_checkpoint()` writes the (loaded) values back. The harness always resumes when a checkpoint exists (`harness_ane.py:130-138`). Therefore **every `LEARNING_RATE` / `TOTAL_STEPS` change made while a checkpoint existed never took effect**. Affected recorded verdicts:

- Phase-1 `LR=8e-4 too aggressive` (discard), `LR=5e-4 with ACCUM=10` (keep) — noise.
- v9/v10-era `5e-4→4.25e-4→4.0e-4→3.8e-4` ladder — measured continuation noise, not LR effects. "3.8e-4 is optimal" is unfounded; no LR was ever actually compared.
- v6_c8 `TOTAL=5000 warmup=50 LR_MIN=0.01` — the TOTAL/warmup parts were no-ops.
- August `LR=3.6e-4` / `3.7e-4` probes (2.3468 / 2.3486) — pure data-order noise; doubly so because the schedule was floored (2.2).

Only fresh runs (checkpoint deleted) honor config LR. WD / SOFTCAP / ACCUM / LOSS_SCALE / EMBED_LR / MATRIX_LR / LR_MIN_FRAC / betas are read live from defines — those verdicts stand.

### 2.2 The cosine schedule is exhausted — the "plateau" is a floor, not a learning-rate optimum

`adam_t` persists across resumes (`--reset-timing` resets timing only, `train_ane.m:284-287`) and increments once per weight update. Live checkpoint: `adam_t=2611`, `total_steps=3000` → `decay_ratio = (2611−100)/(3000−100) ≈ 0.866` → `scheduled_lr ≈ 5.3e-5` (**~14% of peak**), pinned at the `LR_MIN_FRAC` floor (3.8e-5) after ~289 more updates. Every window since June trained (and all August probes trained) at ~floor LR. The June 2.320954 is partly an annealing bonus — the run finished its cosine tail. Further progress on this lineage requires a **warm restart** (reset `adam_t`, LR back to peak, re-anneal), which currently has no CLI flag and needs a small code change.

### 2.3 Fixed RNG seed replays the identical data order every window

`srand48(42 + start_step)` (`train_ane.m:454`) with `--reset-timing` (`start_step=0`) seeds identically each window → the same ~2,270 sequences are replayed in the same order, window after window, over a 17.7M-token train split (only shard `data00` of **50 available shards** is used; `ane/download_data.sh` extracts just `data00.bin` from a 993 MB archive).

### 2.4 ~27% of wall time is hidden optimizer/restage overhead

`ms_per_step` is measured before the Adam/Lion update block (`train_ane.m:718` vs `:728`), so the update cost is invisible in the step metric but visible in wall time:

| Run | steps×ms/step | wall | hidden gap | per update |
|---|---|---|---|---|
| June best (ACCUM=2) | 212.7 s | 291.5 s | **78.8 s (27%)** | ~69 ms |
| Aug ACCUM=1 | 154.6 s | 292.2 s | **137.6 s (47%)** | ~122 ms |

The update block does: full-parameter gradient-averaging pass (66M params), global-norm clip pass, Lion update over 66M matrix + **full 32K×768 embedding (24.5M params, of which only ~compacted rows ever have nonzero grads)**, 12 transposes + 10 IOSurface restages × 6 layers, full-vocab `gembed` memset. At ACCUM=1 the added cost is larger still because `dispatch_group_wait` exposes the dW latency every step instead of overlapping it.

### 2.5 Smaller gotchas

- **3000-step loop cap** (`step < total_steps`, total from checkpoint): at ACCUM=14 runs hit ~2,945 steps — the cap is nearly binding. Any throughput win (e.g. SEQ=256) would waste up to a third of the window unless `TOTAL_STEPS` is raised (fresh runs honor it).
- **`train_loss` in the JSON is the last single sequence's loss**, not a mean — the "train 1.56 vs val 2.35 gap" in logs is one-sample noise, not a reliable overfitting signal.
- **Eval noise**: `VAL_WINDOWS=50` → 25.6K tokens. Differences like 2.3468 vs 2.3486 (the August "LR probes") are far inside the noise band; there is no defined minimal detectable effect.
- `logits`/`dlogits` (65 MB each) allocated but unused under `USE_VOCAB_COMPACT`; per-step malloc/free churn in the hot loop (minor).
- The March utilization plan (`docs/plans/2026-03-12-ane-utilization-improvements.md`) was implemented on branch `autoresearch-ane/mar12-features` (channel-first square weights, RMSNorm fusion, INT8 activations) and **never merged or measured**; it also predates the mega-kernels, so it would need a rebase and partial rework.

## Part 3 — What was missed (summary)

1. A validity bug that silently disabled two of the most-swept knobs (LR, TOTAL_STEPS) — several keep/discard verdicts and the "optimal LR=3.8e-4" conclusion are noise.
2. Schedule exhaustion masquerading as a plateau — no warm-restart mechanism exists.
3. Deterministic data replay + 49 unused data shards (2.5% of available TinyStories tokens in use).
4. The smaller/faster architecture direction was never probed (only bigger, which failed): SEQ=256, NLAYERS=5, DIM=640/HIDDEN=1728 untested post-fusion. "More steps beats bigger" was only verified in one direction.
5. Update-block overhead (~27% of wall) unmeasured and unoptimized; `ms_per_step` hides it.
6. Stranded `mar12-features` branch.
7. Eval noise band undefined → micro-differences over-interpreted.

## Part 4 — Recommended plan (ordered by expected value)

### P0 — Restore experiment validity (needs code change; `train_ane.m` is agent-read-only, so this is a maintainer decision)

1. **Honor config on resume**: don't let `load_checkpoint` overwrite `lr`/`total_steps` (or add `--lr`/`--total-steps` overrides applied after load). Without this, LR research is impossible.
2. **Add `--reset-schedule`** (warm restart): set `adam_t=0` on resume so the cosine re-anneals from peak LR. Harness passes `--reset-timing` already; add the flag next to it.
3. **De-determinize sampling**: seed from `adam_t`/wall clock instead of `42+start_step`.

### P1 — Highest-leverage runs (after P0)

4. **Warm-restart the 2.320954 lineage**: restore anchor, `--reset-schedule`, LR 3.8e-4 (optionally 4-5e-4), full re-anneal over 1–2 windows. Cheapest credible new-best. Can iterate SGDR-style.
5. **Use more data with zero code change**: concatenate shards 01–07 into `tinystories_data00.bin` (flat uint16 stream; harness/binary unchanged; val split auto-moves to the 90% mark) → ~158M tokens instead of 19.7M. Combine with #4.
6. **Real LR sweep** (fresh starts, which honor config LR): {3e-4, 3.8e-4, 5e-4, 7e-4} — the first actual LR comparison of the project.
7. **Unexplored live knobs** under Lion at the anchored lineage, single-variable, anchor-restored protocol (as in August): `ADAM_BETA2` {0.90, 0.98} (Lion momentum never swept — 0.99 was Adam-only), `GRAD_CLIP` {0.5, 2.0} (Adam-only before), `WD` {0.075, 0.15}, `SOFTCAP` {25, 35}, `MATRIX_LR` {0.07, 0.15}, `ACCUM=3`, `LR_MIN_FRAC` {0.05, 0.15}.

### P2 — Throughput (more steps per window at equal quality)

8. **Cut update-block cost**: fold `1/(ACCUM·LOSS_SCALE)` into optimizer LR (drops the full 66M-param averaging pass); update only the ~compact embedding rows instead of all 32K×768; skip the full-vocab `gembed` memset; fuse clip-norm into the averaging pass. Plausible ~2× on the 69 ms/update → ~10% more steps at ACCUM=2, and makes ACCUM=1 competitive.
9. **SEQ=256 arch probe** (checkpoint reset): TinyStories stories are short; halves attention compute/SRAM, expect ~30% faster steps. Must raise `TOTAL_STEPS` in the same change (fresh runs honor it) or the 3000 cap wastes the window.
10. **Smaller arch family**: NLAYERS=5, or DIM=640/HIDDEN=1728 — the untested direction.
11. **Rebase + measure or close `mar12-features`** (channel-first staging still applies; RMSNorm fusion interacts with the fused kernels; INT8 activations is the riskiest).

### P3 — Measurement hygiene

12. Define a minimal detectable effect (~±0.01 at 50 val windows) and stop logging single-sequence `train_loss` as if meaningful (log a window mean instead).
13. Snapshot the best checkpoint automatically on keep (the manual "preserved copy" discipline already exists; make it part of the loop).

## Bottom line

The pipeline work (fusion, dynamic weights, compaction) is genuinely strong, and 6.109 → 2.320954 is real progress. But the last ~30 recorded experiments largely re-measured noise: two swept knobs were silently inert, the schedule was floored, and the data order was frozen. The three cheapest credible paths to a better score are: **warm-restart the anneal (P0.2 + P1.4)**, **feed more of the already-downloaded dataset (P1.5)**, and **cut the hidden 27% update overhead (P2.8)** — in that order. Architecture exploration should go smaller/faster (SEQ=256 first), not bigger.
